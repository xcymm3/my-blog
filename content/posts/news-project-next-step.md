## News 不是做不出来，难的是把它做得值得用

News 项目目前已经有了一个能看的新闻网站：抓取内容、整理页面、展示新闻，基本流程都跑通了。但我最近重新看了一遍，发现真正的问题不在页面做得够不够完整，而在于它离“用户愿意每天打开一次”还有点远。

最直接的限制来自内容。现在主要依赖 RSS 订阅源，优点是稳定、便宜，也不用自己维护复杂的采集系统；问题同样明显：可用的源还是太少，覆盖范围有限，更新速度和内容质量也很难完全控制。做成一个新闻站之后，如果用户看到的永远只是几类固定内容，那它再好看，也很难有持续打开的理由。

## RSS 能解决起步，但撑不起完整的内容体验

一开始用 RSS 是合理的。它让我先把“新闻从哪里来”这个问题解决掉，成本几乎可以忽略，也避免了直接爬网页带来的反爬、版权和维护问题。

但 RSS 更像一个基础供给，不是完整答案。它的核心问题不是技术实现，而是内容密度不够：想覆盖更多领域，就要不断找源、判断质量、处理重复；想让用户搜到具体事件，又会发现 RSS 里的内容并不一定足够及时或足够全面。

表面上看，只要再多接几个源就行。真正麻烦的地方是，源越多，重复新闻、标题党和低质量内容也会一起进来。到最后，站点可能只是从“内容少”变成“内容很多，但没什么可看”。这一步如果没有筛选和聚合能力，堆数据意义不大。

## 搜索 API 能补内容，但账必须先算清楚

搜索 API 是我正在考虑的第二条路。它的优势很直接：内容来源更广，遇到热点话题也能主动检索，不必完全等 RSS 推送。

问题也很现实：调用要花钱，而且费用会跟用户量、搜索次数一起增长。小范围自己测试时，这笔成本不算什么；一旦真的有人频繁使用，搜索请求就会变成一个没有上限的支出。对于个人项目来说，这种成本结构不能只看“现在用得起”，还要看“用户多一点以后会不会失控”。💰

所以我不会一上来就把所有页面都接到搜索 API 上。更合理的做法是先把它放到少量高价值场景里，例如热点补充、专题检索，或者用户主动发起的搜索；同时加缓存、限制请求频率，并给没有命中结果的情况准备 RSS 降级。先验证效果，再决定值不值得扩大调用范围。

## 现在还没用 LangChain，项目的“内容理解”确实不够

目前的 News 更像一个新闻展示和聚合站：能把内容放出来，但还没有真正理解内容、比较不同报道，更谈不上根据用户的问题给出整理后的答案。

这也是我觉得它目前技术含量偏低的原因。不是说一定要为了用 AI 而用 AI，而是新闻天然需要处理大量重复、碎片化的信息。如果只是把 RSS 和搜索结果按时间排好，和普通资讯列表差别不大；用户完全可以直接去原始平台看，为什么要多打开一个网站？

接下来我准备试试 LangChain 加搜索 API 的组合：让搜索负责找资料，让 LangChain 负责把多个来源的结果做去重、分类、摘要和关联。重点不是做一个会聊天的窗口，而是验证它能不能把“同一件事的十条新闻”整理成一份真正有用的阅读结果。🎯

这里也有边界。模型总结得再流畅，如果来源不可靠、链接不可追溯，结果就没有价值。所以后续每次生成内容都应该保留原文来源，必要时让用户能回到原始报道；模型出错时，至少还能退回到普通新闻列表，而不是给出一段看起来很像答案的幻觉内容。

## 现在的优先级

接下来不会盲目加功能，我准备按这个顺序推进：

1. 补充一批高质量 RSS 源，先把基础内容密度拉起来。
2. 接入搜索 API 做小范围测试，记录调用次数、缓存命中和实际成本。
3. 用 LangChain 做“多来源新闻摘要”原型，只选一个热点场景硬碰硬测试。
4. 保留来源链接和失败降级，先保证结果可验证，再谈智能化。
5. 继续想产品亮点。纯新闻网站确实不够特别，最后能留下用户的，可能不是新闻数量，而是它能不能帮人更快看懂一件事。📉

## 当前判断

| 问题     | 现在的状态             | 下一步                            |
| -------- | ---------------------- | --------------------------------- |
| 内容来源 | RSS 稳定但数量不足     | 扩充高质量源，搜索补热点          |
| 搜索成本 | 有能力但不可无节制调用 | 缓存、限流，只投高价值场景        |
| 内容理解 | 目前只是展示和聚合     | 用 LangChain 测试去重、摘要和关联 |
| 产品亮点 | 还不够清楚             | 从“帮用户看懂新闻”寻找方向        |

一句话总结：News 目前最缺的不是再加一个页面，而是证明它比“打开新闻 App”多解决了什么问题。

先把内容供给和成本控制做稳，再拿 LangChain 做一次真实的新闻整理测试。如果效果不明显，就及时收缩，不把复杂度和 API 费用提前背到项目身上。这个项目还在继续试，答案暂时没有定下来，但问题已经比一开始清楚多了。
